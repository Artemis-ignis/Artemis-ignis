# 픽토리 · 원하는 사진을 다시 찾게 만드는 제품 브리프

[제품 사례](pictory.md) · [포트폴리오 홈](../../README.md)

> 작성일: 2026.09.10. 기존 구현·화면·작업 기록을 바탕으로 포트폴리오용으로 재구성한 제품 브리프입니다. 당시 원본 PRD나 이미 실행한 고객 조사 결과를 뜻하지 않습니다.

## 해결하려는 과업

사진이 쌓인 사람이 필요한 컷을 찾아 분류하고 남기는 일입니다. 한 장씩 살펴보는 부담 때문에 정리를 미루게 되는 상황을 줄이려 합니다.

**해결 가설:** 정리 목적에 맞게 사진을 묶고 결과를 바로 검토·보관하게 하면, 사진 탐색과 분류의 부담을 줄일 수 있습니다.

## 사용자 여정과 요구사항

| 단계 | 사용자가 알아야 할 것 | 완료 기준 |
| --- | --- | --- |
| 사진 선택 | 어떤 범위의 사진을 가져오는지 | 권한 거부·가져오기 실패·선택 취소를 구분해 안내 |
| 결과 탐색 | 어떤 기준으로 묶였는지 | 분류별·날짜별 결과를 살펴볼 수 있음 |
| 검토·보관 | 원하는 사진을 남기는 방법 | 선택한 결과와 보관 상태를 확인할 수 있음 |
| 재방문·삭제 | 어떤 데이터가 남았는지 | 저장 결과 복원과 데이터 삭제 범위를 설명할 수 있음 |

## 기술 제약이 제품 설명을 바꾼 사례

[기존 사진 가져오기 정책](https://github.com/Artemis-ignis/pictory-apps-in-toss/blob/main/docs/photo-import-strategy.md)에 따르면, 프로젝트에서 확인한 SDK에는 전체 앨범을 날짜·앨범명으로 검색하는 필터가 없었습니다. 따라서 후보를 가져온 뒤 내부에서 정렬·필터링하고 메모리 부담을 제한하도록 범위를 정했습니다.

이 문서가 제시한 후보 창 상한은 300장입니다. 전체 사진첩 검색을 완료했다고 설명하기보다 **가져온 후보 안에서 정리**한다는 범위를 사용자에게 알려야 합니다. 해당 SDK 제약은 당시 프로젝트 문서 기준이며 최신 플랫폼 사양으로 일반화하지 않습니다.

## 우선순위의 이유

1. **가져오기와 범위 안내:** 사용자가 원하는 사진이 후보에 없으면 분류 품질만 개선해도 과업을 끝내기 어렵습니다.
2. **결과 검토와 보관:** AI 분류의 완료보다 사용자가 사진을 찾고 남기는 행동이 목적입니다.
3. **개인정보와 사용 권한:** 민감 결과 노출을 줄이고 광고·결제 상태와 실제 사용량을 일치시키는 것이 신뢰의 조건입니다.

현재 구현을 바탕으로 다시 정리한 판단 순서이며 과거 의사결정 문서의 원문은 아닙니다.

## 다음 사용자 검증 설계

**과업:** 참가자가 자신이 찾으려는 사진의 목적을 먼저 정한 뒤 사진을 선택하고, 결과에서 원하는 컷을 찾아 보관합니다. 참여자가 공개에 동의한 테스트 사진을 사용합니다.

| 확인 질문 | 관찰할 지표·행동 | 다음 결정 |
| --- | --- | --- |
| 찾으려던 사진이 후보에 있었나? | 가져온 범위와 목표 사진 포함 여부 | 누락이 원인이면 가져오기·범위 안내부터 개선 |
| 결과를 이해하고 찾았나? | 결과 표시부터 목표 사진 보관까지 시간·완료 여부 | 묶음을 이해하지 못하면 분류명·탐색 구조 개선 |
| 분류가 틀렸을 때 어떻게 행동하나? | 재탐색·수정 시도·포기 이유 | 오류를 발견하고 대응할 수 있는 동선 보강 |
| 신뢰를 해치는 상황은 없었나? | 민감 이미지 노출·삭제 기대와 실제 범위의 불일치 | 발생 시 해당 노출·삭제 문제 우선 수정 |

초기에는 관찰 기록으로 원인을 찾고, 기준값을 확보한 뒤 목표를 설정할 계획입니다. 실제 토스 단말의 권한·광고·결제 검증도 출시 전 필요합니다.
