# 딱담아 · 구매 준비를 줄이기 위한 제품 브리프

[제품 사례](ddakdama.md) · [포트폴리오 홈](../../README.md)

> 작성일: 2026.09.10. 기존 구현·화면·작업 기록을 바탕으로 포트폴리오용으로 재구성한 제품 브리프입니다. 당시 원본 PRD나 이미 실행한 고객 조사 결과를 뜻하지 않습니다.

## 해결하려는 과업

장볼 목록을 이미 정한 사람이 원하는 상품과 수량을 확인해 구매 준비를 끝내는 일입니다. 지금은 목록을 쇼핑몰 검색으로 옮기고, 후보를 비교하고, 장바구니를 다시 만드는 작업이 남습니다.

**해결 가설:** 목록을 구조화하고 상품 비교와 담기 전 확인을 연결하면, 사용자가 같은 정보를 여러 번 입력하는 부담을 줄일 수 있습니다.

## 화면으로 구체화한 요구사항

| 사용자 상황 | 필요한 동작 | 완료 기준 |
| --- | --- | --- |
| 여러 품목을 한 번에 적음 | 상품명·규격·포장·구매 수량을 구분해 보여줌 | 사용자가 품목별로 해석을 확인하고 수정할 수 있음 |
| 비슷한 상품이 여러 개 나옴 | 정확 후보와 검토 후보를 구분함 | 확실하지 않은 후보가 확정된 것처럼 넘어가지 않음 |
| 일부 상품의 가격·규격을 확인할 수 없음 | 문제 품목을 표시하고 재선택·재시도 경로를 줌 | 확인된 항목과 해결이 필요한 항목이 구분됨 |
| 장바구니 추가를 실행함 | 실행 결과와 실제 수량 변화를 확인함 | 클릭 성공만으로 구매 준비 완료를 선언하지 않음 |

## 범위와 우선순위의 이유

| 먼저 확인할 것 | 이유 | 뒤로 둘 것 |
| --- | --- | --- |
| 품목과 수량 해석 | 여기서 틀리면 뒤 단계의 편리함이 구매 오류로 이어짐 | 더 다양한 추천 방식 |
| 후보 비교와 사용자 확인 | 원하는 상품임을 판단할 수 있어야 진행할 수 있음 | 불확실한 후보의 자동 확정 |
| 실패 복구와 결과 확인 | 일부 실패가 전체 과업 포기로 이어지지 않도록 함 | 화면 수만 늘리는 확장 |

이는 현재 제품 구조를 설명하기 위해 정리한 우선순위 논리입니다. 당시의 정량 우선순위 점수나 스프린트 계획을 재현한 것은 아닙니다.

## 어떤 증거가 있고 무엇이 남았나

[기존 라이브 테스트 보고서](https://github.com/Artemis-ignis/ddakdama/blob/main/docs/LIVE_TEST_REPORT.md)에는 실제 검색·상세페이지의 상품 정보 확인, 공개 MCP 페어링과 목록 전달, 샘플 기반 장바구니 상태 검증이 구분돼 있습니다. 문서의 마지막 날짜별 절은 2026.07.17이며 상단 기준일은 2026.07.20입니다.

이 기록은 당시 관찰의 근거입니다. 최신 빌드의 실제 장바구니 변경 성공이나 고객 사용 성과를 대신하지 않습니다.

## 다음 사용자 검증 설계

**과업:** 참가자가 실제 구매하려던 목록을 준비하고, 평소 방식과 딱담아로 각각 구매 준비를 수행합니다. 서로 다른 동등 난이도 목록을 사용하고 수행 순서를 번갈아 학습 효과를 줄입니다.

| 확인 질문 | 기록 방법 | 결과가 다음 결정에 미치는 영향 |
| --- | --- | --- |
| 반복 작업이 줄었나? | 과업 시작부터 후보·수량 검토 완료까지의 시간; 완료·중단을 별도 기록 | 검색·입력에서 시간이 남으면 전달 흐름을 개선 |
| 원하는 상품을 찾았나? | 최종 검토 목록과 원래 의도의 품목·수량 일치 여부 | 불일치가 있으면 자동 선택 확대보다 해석·비교를 우선 |
| 막혀도 이어갈 수 있나? | 문제 품목 발생 후 사용자가 복구했는지 관찰 | 복구 실패가 많으면 안내·재선택 동선을 개선 |

계획 단계입니다. 목표 수치는 초기 과업 관찰과 기준값 확보 후 정합니다.
